# EvidenceTrail

EvidenceTrail is a recruiter-first, no-score evidence review. A recruiter supplies one job description and up to five CVs. Muse Spark interprets each requirement and can identify potentially transferable experience; EvidenceTrail verifies every displayed quote against the source PDF, preserves gaps and conflicts, and gives the recruiter a reviewable evidence trail.

The report describes supplied documents. It does not score or rank a candidate and it does not make a hiring decision.

For a single-CV review, a recruiter can optionally check a candidate statement against the CV. This stays separate from job-requirement evidence and never establishes real-world truth. A missing CV passage does not mean the claim is false.

Before a CV is uploaded, the free role criteria preflight turns numbered and bulleted job requirements into an evidence-planning worksheet. It preserves the source line, prepares a draft interview question, reviewer evidence check, and candidate self-check, flags exact duplicate lines, and labels priority only when explicit wording appears in the line or its section heading. Reviewers should adapt the draft and use consistent questions and standards. It does not guess priority, score a role, or assess applicants. Only the job text goes to the EvidenceTrail app server; the preflight makes no Meta request and does not save a review. The standalone HTML worksheet contains job criteria only.

An optional wording-reference section can surface exact vague phrases and historical gender-language lexicon cues for human review. It makes no bias score or legal conclusion. Research on language effects is mixed and context-dependent, so cues stay secondary and never label an employer or applicant. The word-list adaptation is MIT-licensed and documented in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Research and market findings that shaped these choices are in [RESEARCH_NOTES.md](RESEARCH_NOTES.md).

For requirements that are not found, conflicting, or ambiguous, EvidenceTrail drafts neutral, job-related follow-up questions. Each stays linked to its requirement and, where available, the verified CV passages that triggered follow-up. Reviewers can copy the questions into a consistent interview process. Any reply recorded in the browser is labeled candidate-provided and unverified, remains separate from CV evidence, and never changes the evidence result.

An optional single-CV checklist gives a candidate accurate ways to clarify missing or conflicting document details. It does not rewrite the CV or encourage unsupported claims.

See [HACKATHON_COMPLIANCE.md](HACKATHON_COMPLIANCE.md) for the rule-focused submission checklist.

## Muse Spark integration and open-source stack

The app is built with open-source Python packages, including FastAPI, PyMuPDF, Pillow, pytesseract, and a Python API client. Muse Spark 1.3 does substantive semantic work in two structured passes: it maps job requirements to candidate passages, then classifies each requirement as direct, related, unsupported, or conflicting using locally retrieved source spans. The second pass also labels the best evidence as specific, stated, keyword-only, or none; a keyword-only mention cannot support a finding. The first pass proposes dated employment episodes and explicit duration claims. EvidenceTrail checks their quotes against the PDF and calculates approximate tenure and date overlap locally; flagged differences are review prompts, not claims of dishonesty. For related findings, Muse must explain the possible transfer and name what remains unproven. EvidenceTrail builds a provenance-bearing block catalog, ranks spans with BM25-style retrieval, rejects unsupported source IDs and quotes, checks the quote on the cited PDF page, and derives the displayed status from citations that pass those checks. The evidence graph links the job-post source to a requirement and then to a verified CV passage. The reviewer controls whether related experience counts for that role; the app does not score or automatically rank candidates. The API key stays server-side, and the report records the model identifier, source fingerprints, and verification audits.

Batch review handles up to five CVs sequentially against one JD. The recruiter sees summaries in upload order, with evidence counts and no overall match score. A requirement-matrix view compares each job need across the batch, shows the explicitly stated priority and job-source line, opens the selected CV's source passage, and reflects the recruiter review state for each finding. Strength chips distinguish specific, stated, keyword-only, and absent evidence using text, color, and an icon; source chips distinguish checked quotes, rejected proposals, and missing accepted passages. The matrix preserves upload order and does not rank candidates. Browser QA remains pending before release. The recruiter can mark each candidate advance, hold for follow-up, or do not advance, add a note, prepare an editable interview invitation from clear direct evidence, and download a shortlist audit JSON with per-requirement evidence, citations, verification results, and invite draft. Each CV's HTML evidence pack remains separately downloadable. One candidate's evidence and reviewer notes stay isolated from another's.

The optional interactive source viewer uses the Mozilla PDF.js 6.4.299 browser build, bundled under `static/vendor/pdfjs/` with its Apache-2.0 license. The viewer code and worker load from this app's own origin; the original CV stays in the browser while it is being viewed. A real analysis sends the CV to the app and Meta Model API only after consent. If the viewer cannot load, the highlighted page images and standalone HTML evidence pack remain available.

Meta's Muse Spark model and input-mode reference: https://dev.meta.ai/docs/models

## Run locally

Requirements: Python 3.11 or newer and Tesseract OCR. A Meta Model API key is required only for real analysis.

On any OS:

1. Create and activate a virtual environment.
2. Install dependencies with pip install -r requirements.txt.
3. To run real analysis, copy .env.example to .env and add your Meta API key as MODEL_API_KEY. Skip this step to explore the synthetic UI preview.
4. Start the app with uvicorn app:app --reload.
5. Open the local address http://127.0.0.1:8000.

The app uses the standard `muse-spark-1.3` model ID. Keep this standard mode for real CVs; Meta’s discounted contributor mode allows submitted content to be used to train future models.

`conflicting` means the CV contains an explicit statement that conflicts with the requirement or contains incompatible claims. A separate **Conflict to clarify** review label can be applied by the deterministic timeline gate when verified dates or durations do not reconcile with a related experience requirement. The UI preserves and displays Muse's original semantic category beneath that label. Missing evidence remains `not_found`; it is not treated as proof that a candidate lacks a qualification.

Source verification confirms that a quoted text span exists in the supplied CV. Muse supplies the semantic interpretation; the reviewer checks whether that passage actually supports or conflicts with the requirement. Neither the model nor the app verifies real-world credentials or employment history.

The default demo guard allows up to 5 analyses per IP per hour, 20 analyses per running app process, and 2 simultaneous analysis pipelines. The concurrency cap covers PDF reading, extraction/OCR, the Muse request, and report rendering. Requests rejected because both pipeline slots are busy do not consume an analysis slot. Once a PDF passes the basic type and size checks, the request reserves a quota slot before parsing/OCR; malformed PDFs and failed Muse attempts count toward the hourly and process limits. The in-memory limits reset when the process restarts; use persistent rate limiting before running this as a public service.

Docker installs English and Arabic Tesseract language data. The app uses OCR only for pages where local PDF text extraction finds no readable text.

## Analysis flow

1. The recruiter selects one CV or a batch of up to five, pastes the job description, and gives explicit consent. For one CV, an optional candidate statement can also be checked.
2. PyMuPDF extracts page text, text blocks, word coordinates, and page dimensions. Tesseract supplies OCR text and word boxes for scanned pages. OCR-derived pages receive an explicit warning in the results and export so reviewers confirm quotes visually and do not treat a failed OCR match as proof of absence.
3. The first structured Muse Spark request receives the original PDF and job description. It proposes atomic requirements and candidate passages that may support, transfer to, or conflict with each requirement. It also extracts explicitly dated roles and explicit duration claims for local timeline checks.
4. Local grounding drops requirements not found verbatim in the job description, removes duplicates, and matches first-pass quotes against the source words. Page hints do not decide where a quote is located. A separate audit checks explicit numbered and bulleted job-description items for strong wording overlap with the model's requirement list. Items without a close wording match are flagged for human review. This lexical check can miss semantic omissions or flag paraphrases; it does not claim complete semantic coverage.
5. EvidenceTrail builds compact source spans from document blocks, keeps page and bounding-box provenance, and ranks candidate spans for each requirement and draft claim with a lightweight BM25-style lexical retriever. The second structured Muse Spark request receives each item and only its allowed candidate source spans, including source IDs, page, bounding box, text, and nearby context.
6. Muse returns a source-linked review. Local checks reject unknown source IDs, quotes absent from their cited span or context, quotes that cannot be located on the cited PDF page, and duplicate citations. The final status is derived from the citations that survive these checks; conflicting claims require explicit incompatible text, while no support remains not found. Uncertain or mismatched results are marked ambiguous for human review. Each requirement also carries the exact job-description source block and its starting line when it can be isolated, so a reviewer can inspect the wording that produced the requirement.
7. A local timeline pass verifies each proposed date and duration quote, parses only supported year/month formats, merges overlapping intervals so months are not double-counted, and flags concurrent roles or self-reported durations longer than the dated work history shown. Year-only endpoints use January boundaries; the UI labels the result approximate and asks for human clarification.
8. The app builds a requirement-to-source graph. Each graph edge can open the original PDF at the cited page and highlight. It also drafts neutral, job-related clarification questions for missing, conflicting, and ambiguous evidence; reviewers can copy them, and the offline pack includes them with their supporting context. These prompts do not claim that a missing CV passage means the candidate lacks the experience, and are not sent automatically.
9. Recruiters can record requirement-level review notes and accept or reject related evidence for that role. They can also record a candidate-level Advance, Hold, or Do not advance decision with a handoff note. The active candidate's decision appears in the batch dossier/matrix and per-CV HTML hand-off; the shortlist JSON contains every candidate decision. Review state is isolated per CV and stays in the current browser session unless included in a download.
10. The report includes the recruiter hand-off summary, both-pass audit counts, verified quotes, page highlights, the timeline review, an optional single-CV statement check, the clarification brief, CV and job-description SHA-256 fingerprints, and the model identifier.
11. The free role criteria preflight sends only the job text to the EvidenceTrail app server. It makes no Meta request, extracts numbered/bulleted lines into an evidence plan, drafts repeatable interview questions, reports explicit line or section-heading priority wording without inferring importance, flags exact duplicates, and can export a standalone job-only worksheet. An optional, secondary language reference gives exact wording cues with human-review questions; it does not label employers or candidates.

## Human review record

Reviewers can mark each evidence trail as not reviewed, evidence reviewed, or needing follow-up, then add a short note. For each candidate—including a single-CV review—the recruiter can also record Advance, Hold for follow-up, or Do not advance, with a handoff note. **Prepare interview invitation** creates an editable, copyable draft from up to three clear, specific, source-anchored direct findings; if none qualify, it uses neutral role wording. Preparing the draft records the recruiter's explicit Advance decision. EvidenceTrail does not send it or schedule an interview. In batch review, the decision appears in the upload-order dossier and matrix; the shortlist audit JSON records every candidate decision and edited draft. The per-CV HTML pack adds a recruiter hand-off summary with the decision, invitation draft, evidence counts, accepted related findings, and follow-up questions. These are recruiter-entered records; they do not change Muse's findings or rank candidates. Notes and decisions stay in the current browser tab until downloaded. Candidate-provided replies are kept in a separate, explicitly unverified section of the pack.

The PDF is sent inline to Meta Model API for analysis with API-side output storage explicitly disabled. EvidenceTrail does not write uploaded CVs to a database, object store, or persistent application file path. FastAPI's multipart UploadFile handling uses a spooled temporary file, so an upload may be held in memory or temporarily placed on the host's temporary disk while the request is parsed and processed ([FastAPI upload-file documentation](https://fastapi.tiangolo.com/tutorial/request-files/#file-parameters-with-uploadfile)). The PDF and job description are sent to Meta only after the user consents; the optional application draft is also sent when supplied. The app does not intentionally retain a durable copy after handling the request; temporary-file cleanup depends on the request/runtime lifecycle.

## Hosting

The repository includes a Render Blueprint at `render.yaml`. It defines a Docker web service in Singapore, uses the existing `/health` endpoint, and sets analysis concurrency to one. Deploy it without a model key to open the UI and synthetic result preview; real analysis remains disabled until the server key is added.

When you are ready for live Muse requests, add `MODEL_API_KEY` in the Render service's Environment page and redeploy. Never commit the key to GitHub or put it in browser code. The Dockerfile installs the OCR dependencies and binds Uvicorn to Render's `PORT`.

The Blueprint requests Render's free web plan. Free services may sleep when idle, so open the demo before a live walkthrough. The app stores no candidate data persistently and needs no attached disk.
