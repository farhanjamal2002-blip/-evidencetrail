# EvidenceTrail

EvidenceTrail is a recruiter-first, no-score CV review workflow. A recruiter supplies one job description and up to five CVs, reviews a shared job checklist, checks each evidence label against its cited page, records Advance, Hold, or Do not advance, and exports an evidence pack. Candidates remain in upload order; EvidenceTrail does not score or rank them.

**Current mode: local workflow simulation.** New reviews use deterministic heuristics only; they do not understand paraphrases, infer transferable skills, or make a hiring assessment. No model calls are made. The Muse integration is kept in the code but is disabled by default. The visible saved Muse replay contains historical results from real calls and makes no new request.

The report describes supplied documents. It does not score or rank a candidate and it does not make a hiring decision.

EvidenceTrail is deliberately a focused evidence-review layer, not a replacement ATS. Criteria-based review, candidate stages, and rejection reasons are established patterns: [Ashby documents per-criterion AI evaluations with reasoning and filtering](https://docs.ashbyhq.com/ai-assisted-application-review), while [Greenhouse documents an application-review stage with advance/reject actions and reasons](https://support.greenhouse.io/hc/en-us/articles/4401963991707-Application-review-stage). EvidenceTrail's design centers the chain between the role criterion, checked source passage, deterministic conflict checks, and the recruiter's recorded action. We do not claim those individual ingredients are unique across the market. The hackathon build uses uploads and local exports; a future KUL integration would keep KUL as the candidate and stage system of record.

Before CV analysis, the local role criteria checklist turns numbered and bulleted job requirements into editable criteria. It preserves source lines, flags exact duplicate lines, and identifies priority only when explicit wording appears in the line or its section heading. It does not score a role or assess applicants. The preflight makes no Meta request and does not save a review. The standalone HTML worksheet contains job criteria only.

Research and market findings that shaped the evidence-review workflow are in [RESEARCH_NOTES.md](RESEARCH_NOTES.md).

See [HACKATHON_COMPLIANCE.md](HACKATHON_COMPLIANCE.md) for the rule-focused submission checklist.

## Analysis engines and open-source stack

The app is built with open-source Python packages, including FastAPI, PyMuPDF, Pillow, pytesseract, and a Python API client. In the current local mode, deterministic rules exercise document extraction, source-location checks, date arithmetic, reviewer controls, and report export. They are not semantic analysis.

When deliberately enabled, Muse Spark 1.3 returns one structured assessment per CV. EvidenceTrail applies deterministic scope and timeline gates, then checks each proposed quote against the original PDF page. The interface separates three layers: Evidence Status (Direct, Related, Conflict to clarify, Unsupported, Not found), Source Check (Verified by page or Blocked), and the recruiter's decision (Advance, Hold, Do not advance). A failed citation cannot pass because Muse says it is valid. The app does not score or rank candidates. The API key stays server-side; reports record the model identifier, source fingerprints, and verification audits.

Batch review handles up to five CVs in bounded parallel against one job description. The browser submits each CV separately, displays completed analyses as they arrive, and preserves upload order; one slow CV does not block review of the others. A short-lived in-memory browser cache can reuse an identical CV + job + rubric result for 15 minutes without another API request. The matrix compares each job need across the batch and opens the selected CV's source passage. It shows evidence status, deterministic source-check state, and each recruiter's decision without a score or aggregate rank. Advance, Hold, and Do not advance can be linked to role criteria; the decision, reason, note, and timestamp appear in the handoff and shortlist audit. Each CV's HTML evidence pack remains separately downloadable, and candidate records stay isolated.

The optional interactive source viewer uses the Mozilla PDF.js 6.4.299 browser build, bundled under `static/vendor/pdfjs/` with its Apache-2.0 license. The viewer code and worker load from this app's own origin. After consent, the uploaded PDF is processed by EvidenceTrail for page-aware extraction and local verification; Muse receives the extracted, page-labelled text, not the original PDF bytes. If the viewer cannot load, the highlighted page images and standalone HTML evidence pack remain available.

Meta's Muse Spark model and input-mode reference: https://dev.meta.ai/docs/models

## Run locally

Requirements: Python 3.11 or newer and Tesseract OCR. No API key is needed for the default local simulation.

On any OS:

1. Create and activate a virtual environment.
2. Install dependencies with pip install -r requirements.txt.
3. Copy .env.example to .env if you want to change settings. The default is local simulation. No Muse request is made unless both `EVIDENCETRAIL_PROVIDER=muse` and `EVIDENCETRAIL_ENABLE_MUSE=true` are set along with a server-side `MODEL_API_KEY`.
4. Start the app with uvicorn app:app --reload.
5. Open the local address http://127.0.0.1:8000.

The app uses the standard `muse-spark-1.3` model ID. Keep this standard mode for real CVs; Meta’s discounted contributor mode allows submitted content to be used to train future models.

`conflicting` means the CV contains an explicit statement that conflicts with the requirement or contains incompatible claims. A separate **Conflict to clarify** review label can be applied by the deterministic timeline gate when verified dates or durations do not reconcile with a related experience requirement. In a Muse run, the UI preserves and displays Muse's original semantic category beneath that label. Missing evidence remains `not_found`; it is not treated as proof that a candidate lacks a qualification.

Source verification confirms that a quoted text span exists in the supplied CV. In an enabled Muse run, Muse supplies the semantic interpretation and the reviewer checks whether that passage actually supports or conflicts with the requirement. In default local mode, heuristics do not assess meaning. Neither the model nor the app verifies real-world credentials or employment history.

The local app default allows up to 5 analyses per IP per hour, 20 analyses per running app process, and 5 simultaneous analysis pipelines. The Render Blueprint deliberately sets analysis concurrency to one; both the 18.656-second saved five-CV run and the separate 11.957-second route-level run were measured locally and are not Render capacity benchmarks. The UI reads the server's concurrency cap and schedules candidates accordingly, so the hosted five-CV flow will run sequentially; summing the latest individual timings suggests roughly 55–57 seconds, but that is an extrapolation, not a Render measurement. A direct client that exceeds the cap receives HTTP 429 rather than entering a server queue. The concurrency cap covers PDF reading, extraction/OCR, the Muse request, and report rendering. Requests rejected because all pipeline slots are busy do not consume an analysis slot. Once a PDF passes the basic type and size checks, the request reserves a quota slot before parsing/OCR; malformed PDFs and failed Muse attempts count toward the hourly and process limits. The in-memory limits reset when the process restarts; use persistent rate limiting before running this as a public service.

Docker installs English and Arabic Tesseract language data. The app uses OCR only for pages where local PDF text extraction finds no readable text.

## Analysis flow

The recruiter-facing sequence, decision boundaries, and current pilot limits are written in [the standalone workflow specification](calibration/standalone_recruiter_workflow_v1.md).

1. The recruiter pastes the job description, optionally prepares and edits the local role checklist, chooses shared or independent criteria, and selects one CV or a batch of up to five. Before a live run, the recruiter explicitly consents to send the locally extracted page-labelled CV text and job criteria to Meta.
2. PyMuPDF extracts page text, text blocks, word coordinates, and page dimensions. Tesseract supplies OCR text and word boxes for scanned pages. OCR-derived pages receive an explicit warning in the results and export so reviewers confirm quotes visually and do not treat a failed OCR match as proof of absence.
3. In the default local mode, deterministic extraction and heuristics exercise the document and review flow; no semantic claim is made. When Muse is deliberately enabled, one structured request per CV receives the job description, selected job criteria, and locally extracted page-labelled CV text. Muse also proposes explicitly dated roles and duration claims for local timeline checks.
4. Local grounding drops requirements not found verbatim in the job description, removes duplicates, and matches first-pass quotes against the source words. Page hints do not decide where a quote is located. A separate audit checks explicit numbered and bulleted job-description items for strong wording overlap with the model's requirement list. Items without a close wording match are flagged for human review. This lexical check can miss semantic omissions or flag paraphrases; it does not claim complete semantic coverage.
5. Muse returns one structured semantic assessment per job requirement, including an evidence label, concise explanation, and quote candidates. It may include date-span proposals for local timeline checks. The response is bounded by a strict schema and local size limits.
6. Local checks reject malformed or unsupported proposals, locate each quote in the extracted word stream, and replace page hints with verified source locations. A failed quote is excluded from evidence and marked for review; it cannot pass because Muse says it is valid. Each requirement also carries the exact job-description source block and its starting line when it can be isolated.
7. A local timeline pass verifies each proposed date and duration quote, parses supported year/month formats, merges overlapping intervals so months are not double-counted, and flags concurrent roles or self-reported durations longer than the dated work history shown. Year-only endpoints use January boundaries; the UI labels the result approximate and asks for human clarification.
8. The app builds a requirement-to-source graph. Each graph edge can open the original PDF at the cited page and highlight the verified quote.
9. Recruiters can record requirement-level review notes and accept or reject related evidence for that role. They can also record a candidate-level Advance, Hold, or Do not advance decision with a handoff note. The active candidate's decision appears in the batch dossier/matrix and per-CV HTML hand-off; the shortlist JSON contains every candidate decision. Review state is isolated per CV and stays in the current browser session unless included in a download.
10. The evidence pack includes the recruiter hand-off summary, single-pass audit counts, verified quotes, page highlights, the timeline review, CV and job-description SHA-256 fingerprints, and the model identifier.
11. The local role criteria preflight sends only the job text to the EvidenceTrail app server. It makes no Meta request, extracts numbered/bulleted lines into an editable checklist, reports explicit line or section-heading priority wording without inferring importance, flags exact duplicates, and can export a standalone job-only worksheet.

## Human review record

For each candidate, the recruiter records Advance, Hold, or Do not advance, with an optional job-related reason, criterion links, and handoff note. In batch review, the decision appears in upload order; the shortlist audit JSON records every candidate decision. The per-CV HTML pack includes the recruiter hand-off summary and evidence trail. These are recruiter-entered records; they do not change Muse's findings or rank candidates. Notes and decisions stay in the current browser tab until downloaded.

After consent, EvidenceTrail sends page-labelled text extracted locally from the CV and the job description and criteria to Meta Model API, with API-side output storage explicitly disabled. The original PDF stays in the EvidenceTrail request flow for local quote verification and source viewing; it is not attached to the Muse request. EvidenceTrail does not write uploaded CVs to a database, object store, or persistent application file path. FastAPI's multipart UploadFile handling uses a spooled temporary file, so an upload may be held in memory or temporarily placed on the host's temporary disk while the request is parsed and processed ([FastAPI upload-file documentation](https://fastapi.tiangolo.com/tutorial/request-files/#file-parameters-with-uploadfile)). The app does not intentionally retain a durable copy after handling the request; temporary-file cleanup depends on the request/runtime lifecycle.

## Hosting

The repository includes a Render Blueprint at `render.yaml`. It defines a Docker web service in Singapore, uses the existing `/health` endpoint, sets analysis concurrency to one, and opts into strict IP parsing of Cloudflare's `CF-Connecting-IP` header for the per-IP demo request cap. That header is trusted only in this Render deployment; local development uses the socket peer address. The per-IP and process-wide caps are in-memory demo controls and must move to a shared store before running multiple instances. Deploying it with the default settings opens the local workflow simulation and saved replay. A server key alone does not enable live Muse calls.

To activate live Muse requests, set `EVIDENCETRAIL_PROVIDER=muse`, `EVIDENCETRAIL_ENABLE_MUSE=true`, and `MODEL_API_KEY` in the Render service's Environment page, then redeploy. The current default remains local-only. Never commit the key to GitHub or put it in browser code. The Dockerfile installs the OCR dependencies and binds Uvicorn to Render's `PORT`.

The Blueprint requests Render's free web plan. Free services may sleep when idle, so open the demo before a live walkthrough. The app stores no candidate data persistently and needs no attached disk.
